## Cross-cutting decisions

These are proposals. Each one fills a gap between the design and today's backend, so each needs a "yes" before implementation starts.

### D1. Roles become permissions
- **What the design needs:**
  - 5 seeded roles: owner, branch_manager, sales_staff, warehouse_staff, accountant.
  - Custom roles.
  - A matrix of module × action.
- **Change:** replace `@RequireRoles` with `@RequirePermission('<module>.<action>')` (ADR-0004 step 5).
  - Modules: `dashboard`, `products`, `inventory`, `orders`, `pos`, `channels`, `customers`, `purchasing`, `staff`, `reports`.
  - Actions: `view`, `create`, `update`, `delete`, `approve`.
- **Migration:**
  - `manager` → `branch_manager`
  - `cashier` → `sales_staff`
  - `owner` keeps every permission
- **Tokens** gain the claims `perms` (permission codes) and `branches` (the branch ids this person may act in).
- **New ADR needed:** whether store users stay `Account` + `AccountTenant`, or become the ERD's separate `Staff` identity. This spec assumes **Account + AccountTenant, extended with `code`, `status`, `branchIds` and `roleId`**, because that is what is built. Under this assumption the ERD's `Staff`, `StaffRole` and `StaffBranch` collapse into it.

### D2. Branch scope
- The tenant still comes only from the token.
- Branch-scoped screens send `branchId` as a query parameter or body field. The service checks it against the token's `branches` claim; owners may use any branch of the tenant. A branch outside the user's scope → **404**.
- The top-bar branch switcher is client state. It is not a token switch.

### D3. Platform admin
- **Separate identity:** `PlatformAdmin`, logging in through `POST /platform/api/v1/admin/auth/login`. Its tokens have `sub_type = platform_admin` and **no `tid`**.
- **Separate route prefix:** admin routes live under `/<service>/api/v1/admin/...`, guarded by `@RequirePlatformAdmin()`. Tenant routes reject these tokens.
- **Reading across stores:** an admin route may read across tenants only through an explicit `AdminRepository`, never through `TenantScopedRepository`. Every admin write is audit-logged with `tenant_id = null` or the target tenant.
- **Platform-wide aggregates** come from read models in `insight`, fed by events:
  - transactions per day, all stores
  - failed jobs across services
  - usage per tenant

  This keeps "no cross-schema joins" intact.
- **Support sessions** (read-only access to a store) issue a short-lived token with `tid = <tenant>`, `sub_type = platform_admin`, `perms = *.view` and ADR-0004's existing `act` claim set to `{ sub: <adminId>, ssn: <sessionId> }`. Every service treats such a token as read-only.

### D4. Readable codes
- Every entity with a code shown in the design gets a per-tenant sequence. Platform-level codes use a global sequence: TN, US, SUB, PAY, JOB, SESSION.
- Codes are generated by the server, unique per tenant, and searchable with `q`.

### D6. Gaps the ERD still does not model on purpose
- **System monitoring numbers** (API p95, 5xx rate, concurrent users, Postgres connections, Redis memory) come from observability, not from service databases. `GET /insight/api/v1/admin/system-health` proxies them. The source (CloudWatch or OTel) is chosen at deploy time.
- **Subscription payments are recorded manually** by an admin. No payment gateway is in scope.

### Suggested build order

The order fits the [roadmap](2026-10-10-catalog-commerce-roadmap.md). Each step still needs its own design spec before code.

1. **Platform RBAC and staff** (D1, D2): permissions, roles, invitations, the `context` endpoint, and real forgot / reset / verify flows. Everything else checks permissions, so this goes first. Needs the Account-vs-Staff ADR.
2. **Catalog (P2):** products, variants, images and lookups. Then switch stock and order lines from SKU text to `variantId`.
3. **Inventory (P3):** stock list and summary, receipts with approval, thresholds, ledger read, transfers, stock takes, then suppliers and POs.
4. **Customer (P4):** customers, groups, tags, loyalty.
5. **Sales (P5):** order lifecycle on the three status axes, manual orders, payments, returns, registers, shifts, POS checkout.
6. **Insight (P6):** hourly / channel / product summaries, dashboard KPIs, attention feed, notifications.
7. **Integration:** channel connections, OAuth, SKU mapping, sync jobs. This is roadmap "deferred"; the design pulls it in.
8. **Platform admin** (D3): admin identity, then tenants, plans and subscriptions, then insight read models, then support sessions. Needs the admin ADRs listed in [04](2026-10-28-api-contracts/04-platform-admin.md).

### ADRs this spec implies
- **Store user identity:** Account + AccountTenant vs Staff (D1).
- **Permissions model** and the `perms` / `branches` claims (ADR-0004 step 5).
- **Platform admin identity, `/admin` routes and cross-tenant reads** (D3).
- **Support-session read-only tokens** (D3).
- **Readable code sequences** (D4), which replace the `DH-<base36>` order code.
