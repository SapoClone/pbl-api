Two stock models coexist in the service; this matters for every rule:
- LEGACY (P1) branch model: table `stock_item` (branch_id + sku string, integer qty), `inventory_ledger`, `stock_reservation`. Used by `POST /api/v1/stock-receipts` with `branchId`, `GET /api/v1/stock`, `POST/DELETE /internal/reservations`, and the `sales.order.completed` consumer.
- M2 warehouse model: `warehouse`, `stock_balance` (warehouse_id + sku_id uuid, numeric(18,3)), `stock_balance_ledger`, documents, `warehouse_reservation`. Used by everything else, including the stock views and the new POS checkout (`/internal/v1/reservations`).

## 3. Scenarios walked through the code

S1. New branch with no warehouse, then a sale.
Platform creates the branch and emits `platform.branch.created`; inventory only writes `branch_projection` (handler:20-70). No warehouse exists. Stock views for the branch return nothing; `POST /stock-thresholds` for it answers 400 `WAREHOUSE_NOT_FOUND` "has no active warehouse" (stock-views.service.ts:586). A sale needs a `warehouseId` in the request; sales never derives a warehouse from the branch. With no warehouse the cashier has nothing to send, and the legacy branch route would answer 409 `I002` (no `stock_item` row). RESULT: cannot sell until someone creates and stocks a warehouse by hand (BR-WH-06).

S2. Deactivate a warehouse that holds stock.
`PATCH /warehouses/:id {status:'INACTIVE'}` with on_hand 5: 409 `WAREHOUSE_HAS_PENDING_OPERATIONS`, details `reason: NON_ZERO_STOCK_BALANCE` (warehouses.service.ts:340-347). After the stock is issued to 0, it succeeds. If only a DRAFT receipt is pending it succeeds and that draft later fails at post with 409 `WAREHOUSE_INACTIVE`.

S3. Issue more than available.
Warehouse has on_hand 10, reserved 4, issue of 7: available 6 < 7 -> 409 `INSUFFICIENT_STOCK`, details list `{requestedQty:'7.000', availableQty:'6.000'}`; nothing changes (issuing.service.ts:205-258). The DRAFT issue stays DRAFT.

S4. Two concurrent issues of the last unit.
Both post from separate DRAFT issues. Post takes `FOR UPDATE` on the balance (issuing.service.ts:212); the second waits, then sees available 0 and answers 409 `INSUFFICIENT_STOCK`. Same for two reservations: Test A (inventory.int-spec.ts:1415) proves 1 success, 1 failure. Result: no oversell.

S5. Receipt approved twice.
Two concurrent `POST /stock-receipts/:id/approve`: the row is locked; the second sees POSTED and gets 409 `STOCK_RECEIPT_INVALID_STATE` (documents.service.ts:159-166); stock rises once (Test G, :1707, for the `/post` route returns 409 `STOCK_RECEIPT_ALREADY_POSTED`). With the same Idempotency-Key on `/post` the second call returns the posted receipt (200).

S6. Two concurrent FIRST receipts of a new SKU into a warehouse (defect).
Both `post` calls take `FOR UPDATE` on `stock_balance`, but no row exists, so no lock is taken. Each computes new on-hand from 0. First inserts; second hits `ON CONFLICT DO UPDATE SET on_hand_qty = $5` (receiving.service.ts:337-345), which overwrites with its own number. Receipts of 5 and 7 can end at 7 (or 5) while the ledger shows both. Different DRAFT receipts are locked separately, so nothing else serialises them. Not covered by a test.

S7. Stock take adjusting reserved stock.
Warehouse on_hand 10, reserved 4. Count of 3: approve fails 409 `STOCKTAKE_BELOW_RESERVED` ("counted 3 is below reserved 4", details with skuId). Count of 6 passes: variance -4, ledger STOCKTAKE_ADJUSTMENT delta -4.000, reserved stays 4, valuation = 6 x avg. If a sale held stock after the snapshot, version differs and the approve answers 409 `STOCKTAKE_STALE_SNAPSHOT` unless `forceRebase:true`. Counting 0 for a SKU with reserved > 0 is refused.

S8. Restricted manager reads another branch's stock.
Manager scoped to branch A calls `GET /stock-levels?branchId=B`: `assertBranch` throws 404 `NOT_FOUND` (stock-views.controller.ts:147-151; test stock-views.int-spec.ts:277). Without `branchId`, the SQL adds `w.branch_id = ANY(A)`, so only A rows come back. `GET /warehouses/<B-warehouse>`: 404. `GET /stock-balances?warehouseId=<central>`: 404 because central has no branch (warehouse-scope.ts:107-111). Receipt/issue/PO ids of B: 404. Never 403.

S9. Warehouse default switch.
Branch has WH-1 default. `POST /warehouses {code:'WH-2', branchId, isDefault:true}`: WH-1 flag cleared then WH-2 inserted default, in one transaction (test inventory.int-spec.ts:904-925). `PATCH WH-2 {isDefault:false}` leaves the branch with no default; nothing refuses it. Two concurrent switches could leave two defaults (no index).

S10. Average cost after a receipt at a different price.
Warehouse has 10 @ avg 100,000. Receipt 10 @ 120,000 posted: new avg = (10x100000 + 10x120000)/20 = 110,000, valuation 2,200,000 (unit test inventory-domain.spec.ts:72). A later issue of 5 keeps avg 110,000, valuation 1,100,000, issue line unit_cost 110,000. A fractional case rounds half-up to whole VND, and valuation = round(on_hand x avg) can differ from the sum of lines by a few VND.

S11. Stock added through `/stock-balances/receipts` then a real receipt.
Direct receive of 10 (no cost) then receipt 10 @ 100,000: avg = 50,000, valuation 1,000,000 for 20 units; the first 10 carry zero cost silently. Anyone with `inventory.create` can do this with no approval, no document and no maker-checker (stock.controller.ts:125-143).

S12. Branch deactivated or deleted in platform.
Platform sets status inactive/deleted and emits the event; `branch_projection.status` is updated. Its warehouses stay ACTIVE; receipts, issues, reservations and sales continue; stock views still list the branch. Only creating a NEW warehouse for that branch is refused (409 `WAREHOUSE_INACTIVE`, message "Branch ... is not active"), and the legacy branch receive is refused with 400 `I001`. Stock in a deleted branch becomes invisible to a restricted manager of that branch only if their branch list is trimmed elsewhere.

S13. Posting a PO receipt twice with the same key.
Partial receive of 4/10 with key K -> PO PARTIALLY_RECEIVED, received 4. Retry with K: code locks the PO, updates `received_qty` to 8 (4 + 4), then `createReceiptInTx` finds key K and returns the old receipt, so on-hand stays +4 while PO says 8 received. A third retry can reach 12 > 10 only if the over-receipt check allowed it; it refuses at remaining 2 with 409 `OVER_RECEIPT_NOT_ALLOWED` ... after the damage of the second call.

S14. QUARANTINE warehouse with a branch.
`POST /warehouses {kind:'QUARANTINE', branchId:A}`: accepted. Its balance is added to branch A's `stock-levels` on_hand and available (stock-views.service.ts:118-125), so quarantined goods show as sellable stock at the branch.

S15. Same warehouse code posted by another branch.
Manager of A posts code `WH-B` (belongs to branch B) with `branchId:A`: passes scope checks, upsert changes branch_id to A, name, kind. Branch B loses a warehouse, its stock and open documents follow the warehouse to A (balances reference the warehouse id).

S16. Restricted cashier sells from central stock.
Order in branch A with `warehouseId` of the CENTRAL warehouse: sales validates branch and shift only; inventory reserves from any ACTIVE warehouse with the internal token. Stock of central decrements. No branch/warehouse relation check.

## 5. Open questions for the business owner

1. Should creating a branch automatically create a default BRANCH warehouse (code from the branch code) in inventory? Recommended: yes, created by the `platform.branch.created` handler, idempotent by branch id.
2. When a branch is deactivated or deleted, must its warehouses be deactivated too (only if stock is zero), and should a branch with stock be refused deactivation? Recommended: yes for both; deactivation of the branch is blocked with a clear message while stock or open documents exist.
3. May a QUARANTINE or CENTRAL warehouse belong to a branch? Recommended: no; `kind = BRANCH` is the only kind with a branch, and only BRANCH warehouses count in the branch's stock.
4. Is a duplicate warehouse code in the same store an error (409 `WAREHOUSE_CODE_CONFLICT`)? Recommended: yes, never overwrite.
5. Should a sale be allowed only from a warehouse of the order's branch (and never from CENTRAL/QUARANTINE)? Recommended: yes.
6. May a user with `inventory.approve` post a DRAFT receipt/issue directly without submit/approve steps? Recommended: yes only for issue; for receipts require the submit step.
7. Should the person who created a receipt, stock take or purchase order be forbidden to approve it? Recommended: no by default, a tenant setting later.
8. Is a direct "add stock without a document" endpoint acceptable (`POST /stock-balances/receipts`)? Recommended: no; remove it or require approval, cost and a document.
9. Should the minimum-stock alert fire every time available crosses below the minimum (once per crossing)? Recommended: yes.
10. Should a stock take freeze sales and other movements in its warehouse while COUNTING? Recommended: no freeze by default; stale check on on-hand only (ignore reservations), and `forceRebase` needs `inventory.approve`.
11. Is one default warehouse per branch mandatory? Recommended: yes, the first warehouse of a branch becomes default automatically, and the default cannot be unset without naming another.
12. Does a transfer discrepancy count as loss in the books? Recommended: yes, record a loss movement at average cost when the discrepancy is closed.
13. Should a held reservation be able to complete when the warehouse (or the branch) was deactivated meanwhile? Recommended: yes, commit and release stay allowed; only new holds are refused (current behaviour).
14. Should the legacy `stock_item` branch model be retired? Recommended: yes once sales finishes moving to `/internal/v1/reservations`; until then, show both numbers nowhere to the user.
