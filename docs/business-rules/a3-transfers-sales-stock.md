**Architecture fact that governs everything below.** Inventory has TWO unconnected stock stores (ADR-0014 keeps the old one for backward compatibility):
- **Branch/SKU-code store** `stock_item`/`stock_reservation`/`inventory_ledger`, integer quantities, keyed by (branch, sku code). Used by `POST /internal/reservations`, by `POST /api/v1/stock-receipts` with `branchId`, and by the `sales.order.completed` event handler.
- **Warehouse/SKU-id store** `stock_balance`/`warehouse_reservation`/`stock_balance_ledger`, decimal(18,3), keyed by (warehouse, variant id). Used by transfers, receipts with `warehouseId`, stock takes, `/internal/v1/reservations`, and the warehouse checkout flows.
Nothing copies between them (grep: `stock_item` appears only in the legacy files). Transfers only touch the warehouse store.

## 3. Scenarios walked through the code

1. **Transfer more than available.** Create succeeds (no stock check, `transfers.service.ts:44-98`). Dispatch: header locked, each source balance locked and compared; a short line collects into `shortages`; throw 409 `INSUFFICIENT_STOCK` with every short line before any UPDATE (`:200-216`). Nothing changes and the transfer stays DRAFT. If the stock is reserved by sales holds, the available figure excludes it, so held units are refused too.
2. **Dispatch twice.** Second call (or a concurrent one, after the lock) sees `DISPATCHED`, 409 `TRANSFER_INVALID_STATE` (`:121`, `inventory-domain.ts:638-646`). No double deduction.
3. **Receive at a branch the receiver cannot access.** Controller calls `assertTransfer(branches, id, 'to')`; the destination branch is not in the member's list, so 404 `NOT_FOUND` "Stock transfer not found" (`warehouse-scope.ts:112-139`). A source-branch member is refused too. Destination with no branch: unrestricted members only.
4. **Receive a different quantity than dispatched.** More: 409 `TRANSFER_QUANTITY_MISMATCH` (`:493-507`). Less with no discrepancy declared: status PARTIALLY_RECEIVED, units stay in destination `in_transit_qty` indefinitely. Less with `discrepancyQty` covering the rest: DISCREPANCY; units vanish from stock with no ledger line; `resolveDiscrepancy:true` later closes it as RECEIVED.
5. **Source branch sells the in-transit units.** Impossible by construction: dispatch already deducted `on_hand` at the source (`:229-246`). A hold taken before dispatch blocks the dispatch instead. The destination cannot sell them either because `available = on_hand - reserved` ignores `in_transit_qty` (`reservations.service.ts:611-619`).
6. **Transfer to the same warehouse.** 400 `TRANSFER_SAME_WAREHOUSE` at create, before any query (`:45`).
7. **Transfer to a quarantine warehouse.** Accepted. `assertActiveWarehouse` reads `kind` but nobody uses it (grep). A dispatched transfer to a quarantine warehouse receives into on-hand there; that on-hand is then reservable and sellable (scenario 12). Branch reports exclude quarantine only in the views (CLAUDE.md note).
8. **Cancel after dispatch.** `POST /stock-transfers/:id/cancel` on DISPATCHED: 409 `TRANSFER_INVALID_STATE` (`documents.service.ts:215-221`). The goods can only be received; there is no reversal, so an erroneous dispatch needs a reverse transfer from the destination after receiving.
9. **Sale in a branch with no warehouse.** Legacy `POST /orders`: the branch store has no `stock_item` rows, `held === 0`, the shortage reports available 0, 409 `S004` (`reservations.service.ts:239-256`). Warehouse flows: the client must send a `warehouseId`; unknown warehouse gives 404 `WAREHOUSE_NOT_FOUND` from inventory, which sales converts into a generic 503 `S005` "Stock cannot be checked" (`inventory.client.ts:171-178`) and the legacy `checkout` parks the workflow RECOVERY_PENDING forever (it retries the same permanent error, `orders.service.ts:509-526`). An INACTIVE warehouse or a non-sellable SKU is 409 from inventory and sales treats any 409 except `IDEMPOTENCY_CONFLICT` as "insufficient stock" with empty details (`inventory.client.ts:156-171`).
10. **Reservation expires while the cashier is paying.** POS checkout with cash/card is one request (reserve to commit within seconds) so TTL is irrelevant. With a pending tender (state AWAITING_PAYMENT, e.g. QR), stock is reserved first (`checkout.service.ts:429`) and `confirm-payment` commits later (`:534-600`). After 900 s the sweep expired the hold; commit answers 409; sales reads the state EXPIRED and runs `cancelExpiredWorkflow` (`:1316-1327,939-985`): workflow CANCELLED, loyalty/credit released, 409 `STOCK_RESERVATION_FAILED`. The external payment already received is not refunded by this code (not verified elsewhere). Within the 60 s sweep gap the commit still succeeds.
11. **Return to a different branch than it was sold at.** Order in branch A, request `warehouseId` of branch B: sales accepts it (no branch check, `returns.service.ts:379`); inventory accepts it if the caller's scope covers B's warehouse (`stock.controller.ts:91`). A caller with only branch A in scope gets 404 from inventory, shown as 503. Stock lands in B, the sales return stays in branch A.
12. **Two cashiers selling the last unit.** One hold wins; the other gets 409 `S004` and a `REJECTED` workflow with `last_error` holding the shortages (`checkout.service.ts:1258-1272`). Proven by `inventory.int-spec.ts:1415` and `sales.int-spec.ts:644` against real Postgres (not run here).
13. **Inventory down during a sale.** Legacy `POST /orders`: 503 `S005`, no order. Warehouse `checkout`: workflow RECOVERY_PENDING, 503 `CHECKOUT_RECOVERY_PENDING`; a client retry with the same key resumes. POS checkout: tries `GET by-key` to learn the outcome, otherwise 503 and RECOVERY_PENDING. After 5 reconcile attempts it becomes REQUIRES_RECONCILIATION and emits `sales.checkout.reconciliation_required` (`checkout.service.ts:728-764`).
14. **Order committed in inventory but the local transaction fails.** Stock is already deducted, order does not exist; state COMMITTING_STOCK/FINALIZING; reconcile finalizes it using `commitConfirmed` (`:854-934`). Covered by Test M (mocked inventory).
15. **Cancel a confirmed checkout via the legacy route.** `/orders/checkouts/:id/cancel` for a CONFIRMED workflow tries release, inventory answers 409 (hold COMMITTED), sales swallows it, and marks the workflow CANCELLED while the completed order stays (`orders.service.ts:410-440`, `inventory.client.ts:262-270`).
16. **Fulfil a confirmed omnichannel order two hours later.** Hold expired at 15 min (BR-SA-14); `commitWarehouseReservation` gets 409 and throws 503 `S005` (`inventory.client.ts:206-224`); the fulfillment cannot be confirmed, and `confirmOrder` does not re-reserve because the order already holds a `reservationId`.

## 5. Open questions for the business owner

1. Must a sale always draw from the selling branch's own default warehouse (the cashier cannot choose)? Recommended: yes; resolve it from the branch.
2. May any branch sell from the central or quarantine warehouse? Recommended: no (QUARANTINE never sellable, central only by an admin).
3. How long must stock stay held for an order that is confirmed but not yet shipped? Recommended: until it is cancelled or fulfilled (no TTL), or 72 hours with a visible warning.
4. For a QR/bank payment that arrives after the stock hold expired, should the sale be completed if stock is still free, and refunded otherwise? Recommended: yes, re-reserve; refund if still short.
5. May a transfer be cancelled after dispatch (stock returns to the source)? Recommended: yes, by a manager, with a reverse ledger entry.
6. After how many days must a transfer still in DISPATCHED or PARTIALLY_RECEIVED raise an alert? Recommended: 7.
7. Which role writes off units lost in transit, and does the loss need an approval? Recommended: branch_manager approves, valued at dispatch cost.
8. May a branch ship to another branch without the receiving branch having requested it? Recommended: no; the destination branch confirms or an admin creates it.
9. May a transfer go to or from a quarantine warehouse? Recommended: yes only from quarantine to a branch with a manager's approval; never a branch sale from quarantine.
10. Should returned goods be restocked into the branch where the sale was made only? Recommended: yes by default; another warehouse needs a manager.
11. At what cost should returned goods re-enter stock? Recommended: the cost at the original sale.
12. Must a return be approved before it is received? Recommended: yes.
13. Can a cashier (`sales_staff`) receive a return into stock? Recommended: yes, for returns of the cashier's own branch.
14. Is a partial fulfilment allowed, and should it commit only the shipped quantities? Recommended: yes.
15. Should two stock records (branch-level `stock_item` and warehouse `stock_balance`) both stay? Recommended: no, retire the branch-level one and its event handler.
