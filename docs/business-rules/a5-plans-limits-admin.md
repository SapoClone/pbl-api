## 3. Scenarios walked through the code

S-01 Paid plan expires. A basic store has `expires_at` = 2026-12-01 16:59:59Z. On 2026-12-02 nothing happens: no job, status stays `active`, plan stays `basic`, quotas stay 2/10/2000/10 GB, all APIs keep working. The admin screens show `isExpiringSoon: true` and negative `daysLeft`; the `expired` counter shows 0 forever. Only an admin recording a payment or changing the plan changes anything. (BR-PL-17.)

S-02 Downgrade pro to basic with 4 branches. `POST /admin/subscriptions/change-plan` -> `evaluate` -> branches 4 > 2 -> `check.allowed=false` -> 400 `S010`, message "Doanh nghiep dang su dung 4 / 2 chi nhanh cua goi Basic." (first failing key in order branches, users, products, storage). Nothing changes. With exactly 2 branches it passes (`<=`). Admin must first have the store delete/merge branches; there is no "force" flag.

S-03 Admin edits a plan to fewer products than stores hold (basic 2000 -> 1000, store has 1500). Edit succeeds, response `affectedTenantsOverQuota` counts such stores, one `platform.plan.changed` per store is queued. Catalog applies it to stores whose projection row says `basic`. The store keeps its 1500 products; creating the 1501st-and-onward product fails with 409 `Q001 {key:'products', used:1500, limit:1000, planCode:'basic'}`. Platform branch/member limits apply instantly (live read), catalog's after event delivery. Stores with no catalog row are unaffected (S-04).

S-04 A store with no catalog quota row creates products. Allowed without limit, forever (`if (!quota) return;`), and storage is unlimited too. Affects stores older than the projection and any store whose first `subscription.changed` event was never delivered. They get a row only at their next plan event. Admin usage page would still show them as "free, 100 products limit", and a later downgrade check would count their (reported) usage. (D-03.)

S-05 Two concurrent member adds at the limit (free plan, owner + 1 member = 2 of 3). Both transactions call `assertCanAdd(em, tenantId, 'users')`; the advisory lock `quota:<tenant>:users` serialises them; the second sees `used=3` and gets 409 `Q001`. Same for branches and, in catalog, products/storage. Caveat: the two keys `products` and `storage` use different locks, which is fine because they count different things. No automated test for the race.

S-06 Archived products and the limit. Free store with 100 products archives 5: count becomes 95, 5 new products may be created. Archived is irreversible (BR-PL-09), so slot freeing is one-way. INACTIVE and DRAFT products still count. Soft-deleted products do not count. The catalog's "delete product" is actually archive (`products.service.ts:1048`).

S-07 An admin disables the only other super admin. Admin A (super) PATCHes B (super) `status=disabled`: A is active super, so `otherActiveSuperAdmins(B)` = 1 (A) -> allowed; B's sessions are revoked. If A then tries to disable A: `admin.id === callerId && disabled` -> `A011`. If B tries to disable A while B is disabled: B cannot even sign in; with a still-valid access token B is denied by the deny-list. If A is the only active super and a different plain admin tries: refused by role (403), and A011 would also stop it. Net: the platform cannot reach zero active super admins through the API.

S-08 A suspended store's owner with a live refresh token. Suspend ran `revokeAllOfTenant`, so the family is revoked and the session id denied. `POST /auth/refresh` -> `rotate` finds a revoked token -> (reuse path) the family is already revoked, 401. If the owner's family was tenant-less and not revoked: refresh succeeds only for the tenant-less session (no `tenantId` on the row), the new token has no store; `findActiveMembership` excludes suspended stores, so selecting the store fails. Sign-in lists only active-tenant memberships. A token already issued stays valid at most one access-token lifetime unless the deny-list is checked everywhere (not verified); the deny-list entry is written after commit.

S-09 The free store tries to add a warehouse. It has CN01 (isWarehouse=true) = 1/1. `POST /branches {isWarehouse:true}` -> 409 `Q001 {key:'branches', used:1, limit:1, planCode:'free'}`. A "warehouse" and a "store" count the same. It also cannot avoid the limit by deleting CN01 (`assertNotLastActive`) nor by creating-then-deleting. It can only edit CN01 (rename, flip `isWarehouse` to false so it sells, change address). So a free store has exactly one location that is simultaneously its only stock location and its only point of sale. Pro-level behaviours (separate warehouse + shop) need basic (2 branches) or more.

S-10 Storage counted for imports. Import flow: create import upload (IMPORT kind, `PENDING`) -> `PUT content` -> `assertCanStore` counts bytes and sets `UPLOADED` -> `POST /imports` flips it to `ATTACHED`. From then on the CSV's bytes are not counted (and an image becomes `ATTACHED` when linked to a product). The quota check and the usage event therefore measure "files uploaded but not yet used". A free store with a 1 GB limit can upload unlimited image bytes as long as each image is attached before the next upload. Nothing deletes files; stored bytes are never released. (D-01.)

S-11 Admin records payment on a free store. Free subscription has `expiresAt=null`; `!sub.expiresAt` true -> `expiresAt` set to period end, `renewed` event emitted, projection updated. The free plan now has an expiry date that nothing enforces. Same call on a `cancelled`/`expired` row flips it to `active`.

S-12 Plan edit race with a change of plan. `changePlan` evaluates usage, then locks the subscription; a branch added in between (different lock) can make the new plan's limit exceeded by one with no error. Low likelihood (admin-driven). Not tested.

S-13 Store renewal after a plan became hidden. Admin hides `basic`; a store on basic keeps working. Renewing with `change-plan` to `basic` fails `P001`; recording a payment works; moving to a different active plan works.

S-14 Reactivate a store whose paid plan lapsed during suspension. Reactivate returns to `active` (or `trial`); no check of `expires_at`. Time suspended is not credited to the subscription.

S-15 Store creation by an admin for a new email. Owner account created with `password=null` and an `US000nn` code; the owner cannot sign in (no invite email, per decision). An admin can still create the store and the store counts 1 member (owner) against the plan; the passwordless owner occupies a seat.

S-16 Admin signs in 5 times wrong. 5th failure locks 15 minutes and resets the counter; right password during the lock -> `A003`; after the lock, success clears `failedLoginCount`. The `lockoutMaxAttempts` setting edited to 10 changes nothing (BR-PL-37).

## 5. Open questions for the business owner

1. When a paid plan passes `expires_at`, should the store (a) keep working unchanged, (b) get a grace period of N days, then drop to `free`, or (c) be locked read-only? Recommended: (b) with 7 days, then downgrade to `free` limits without deleting data (over-quota data stays, new adds blocked).
2. How many days of grace before the downgrade in question 1? Recommended default: 7 (same as the "expiring soon" amber window).
3. Is there a trial? If yes: how many days, on which plan, and what happens at its end? Recommended: no trial for now; remove the `trial` tab until decided.
4. Should an admin be able to record a payment on a `free` or a closed subscription? Recommended: no (400).
5. Must the payment amount equal plan price x months, or may an admin record any amount (discounts, 0 VND gifts)? Recommended: any amount >= 0 but require a note when it differs from price x months.
6. Should attached images and imported CSVs count toward storage? Recommended: yes (all files kept count until deleted).
7. Should stores that existed before the plan limits (no catalog row) be limited now? Recommended: yes, backfill them to their current plan, with a warning period.
8. Should a store over quota (after a plan edit or downgrade) keep editing existing items and only be blocked from adding? Recommended: yes, as today, and show an upgrade banner.
9. Should a store with a free plan be allowed one extra branch of type warehouse (the default branch being a selling branch)? Recommended: no; keep 1 branch and document it.
10. Should suspending a store also stop integrations (webhook receipt, sync jobs)? Recommended: yes, pause them.
11. Should a demoted or disabled admin lose access instantly? Recommended: yes (revoke sessions on role change).
12. Should the lockout numbers be editable in settings (apply to both admins and store accounts)? Recommended: yes, apply them, keep minimum 3 attempts.
13. Can a super admin disable another super admin without that person's consent? Recommended: yes, as now, provided at least one other active super admin remains.
14. Are plan limits meant to be strict at the exact limit (100 of 100 allowed, 101st refused), as now? Recommended: yes, keep.
15. Should `free` have no expiry date even when an admin runs change-plan to `free`? Recommended: yes (allow null `expiresAt` for zero-price plans).
